**진행 업데이트:** 아래는 구현 전 계획입니다. 1~6의 로컬 기능을 연결한 결과와 미검증 항목은 [구현 설명](evidence-workflow.md)을 보세요.

# 다음 고도화 계획 — 조사 결과를 실제 검토에 쓰게 만들기

2026-10-28 코드·확보 자료 기준 **제안**입니다. 이 문서의 기능이 새로 구현됐다는 뜻은 아닙니다.
모델·지도·OCR의 신규 유료 호출과 Azure 리소스 변경은 하지 않았습니다.

확인된 부분과 미확인 부분을 연결한 뒤, 사용자가 자료를 보완하면 결과가 갱신되는 것입니다.**

## 1. 먼저 후보 하나를 끝까지 연결한다

공정 경로 ID 아래에 같은 사업장·로트·시설·운송 구간·수치·근거·검토 결과를 묶습니다.
원문 근거와 문서별 수치를 가진 로컬 증빙 저장소가 필요합니다.

- **공정:** KG 전이 ID, 단계 순서, 투입·산출 상태와 출처.
- **시설:** 사업장 ID, 명부 ID와 실제 시설의 대응, 수행 공정·투입 규격·허가 자료.
- **활동량:** 투입/산출/잔재물 kg, 함수율·오염도, kWh·연료·물 사용량, 시간 기준.
- **운송:** 각 구간의 출발/도착 게이트·도로거리·차량·적재량·회차, 조회 시각.
- **돈:** 처리비·전처리비·운송비·잔재물 비용·매각 수익, VAT·포장·상하차 포함 여부.
- **탄소:** 공정 LCI 또는 활동량×계수, 질량 기준·지역·기준연도·GWP·할당·운송 포함 여부.
- **증빙:** 원문 파일 해시·쪽/표/셀·관측일·유효성 검토·자료 범위·확인자.

현재 수치 입력의 활동 단위에는 연료 `L`·가스 `m³`가 없습니다. 연료 활동량을 연결하려면
단위 계약·차원 검증·환산 근거를 함께 추가해야 합니다. 단위 이름만 바꿔 넣지 않습니다.
기업 문서는 내부 문서 ID로 연결하고 권한이 있는 원문 조회를 사용합니다.
증빙 링크를 만들기 위해 비공개 문서를 공개할 필요는 없습니다.

같은 업체라도 본사와 처리장·수거 게이트를 구분합니다. 같은 사업장이라도 로트·시기에 따라
수용 규격과 단가가 달라질 수 있습니다. 명부 검색 결과를 실제 수탁 확인으로 승격하지 않습니다.

새 필드의 핵심은 **계수 기준연도와 평가연도의 분리**입니다. 현재처럼 둘의 숫자가 같아야
한다는 검사만 쓰면, 2023년 통계에 기반한 최신 승인 계수를 2026년 검토에 어떻게 대용했는지
표현하기 어렵습니다. 반대로 연도 검사를 없애면 오래된 계수를 무분별하게 쓸 수 있습니다.
출처 기준연도·발표일·평가일·적용 규칙·대용 여부·확인자를 따로 기록하는 방향이 적절합니다.

**완료 기준:** 물량·시설·거리를 바꾸면 관련 비용·탄소만 다시 계산되고, 이전 결과를 현재
결과로 보여주지 않습니다. 알려진 부분 합계와 전체 합계를 구분합니다.

## 2. 미확인 사항을 사용자가 답할 수 있는 질문으로 바꾼다

현재의 긴 체크리스트를 다음 세 묶음으로 바꾸는 것을 제안합니다.

| 종류 | 예시 | 화면에서 할 일 |
| --- | --- | --- |
| 진행을 막는 입력 공백 | 수거 공장·소재 종류·함수율 기준 미확인 | 입력/성적서에서 확인할 항목 지정 |
| 근거가 있는 충돌 | 확인된 시설 규격과 이번 로트의 수분 조건 불일치 | 해당 단계·근거·해결 조건 표시 |
| 비교를 바꿀 수 있는 변수 | 단가·전처리 여부·수율·운송 회차 | 필요한 견적·시험·측정값과 재계산 버튼 표시 |

질문은 보통 3~5개부터 제시하되, 중요한 법규·유해특성 공백은 뒤로 숨기지 않습니다.
우선순위는 추정 손실 확률을 만들어 점수화하지 않고, 필수 조건 여부·영향받는 후보 수·
계산 가능한 손익분기점·자료 확보 가능성으로 설명합니다.

예를 들어 “오염도 확인 필요” 대신 “이 두 경로를 구분하려면 성적서의 오염 성분·함량이
필요합니다. 해당 표를 확인해 주세요”로 안내합니다. 필요한 시험법·허용치는 실제
문헌·규격·법규에서 확인한 경우에만 제시합니다.

**완료 기준:** 질문에 답하거나 문서를 보완하면 해당 후보·단계의 상태가 바뀌고,
어떤 답 때문에 바뀌었는지 근거를 남깁니다. 미확인을 부적합이나 적합으로 바꾸지 않습니다.

## 3. 거리순 업체 목록을 공정 순서의 운송 경로로 바꾼다

지도 API에 연결하는 것 외에도 실제로 선택한 시설 조합 사이의 모든 구간이 필요합니다.
발생지→업체 A와 발생지→업체 B만 비교해서 A→B 전체 경로가 짧다고 판단할 수 없습니다.

먼저 검수한 공정별 시설 후보를 제한한 뒤 실제 연결되는 구간을 조회합니다.
후보를 제한한 이유와 미조회 후보 수를 보존하며 전 지역 최단이라고 부르지 않습니다.
이미 조회한 같은 구간은 공급자 이용조건에 맞는 기간·목적으로만 재사용합니다.

운송 횟수는 차량의 중량·부피 제한과 이번 폐자원 밀도·포장·적재량이 있어야 계산합니다.
최대 적재량만으로 항상 가득 싣는다고 가정하지 않습니다. 지도 통행료와 폐기물 운송업체
견적도 구분합니다. 일반 차량 경로 성공이 폐기물 운반 허가·위험물 통행 승인을 뜻하지 않습니다.

기존 카카오·네이버 어댑터를 먼저 완주시키는 것이 구현 범위가 작습니다.
지원 크레딧 활용을 위해 Azure Maps를 추가하는 것은 선택안입니다.
공식 [한국 지원 표](https://learn.microsoft.com/en-us/azure/azure-maps/routing-coverage)는
최신 Route·한국 데이터 처리 설정을 요구하므로 실제 키·설정·비용·응답 검증이 필요합니다.

**완료 기준:** 동일 로트에서 시설 조합을 바꾸면 전체 구간 거리와 운송 수치가 갱신됩니다.
도로 조회 실패·도로 단절·좌표 미확인·일부 미조회는 그대로 표시됩니다.

## 4. 완벽한 가격·탄소 하나보다 비교 조건과 범위를 계산한다

순비용은 `전처리 + 처리 + 운송 + 잔재물 비용 - 실제 산출물 매각 수익`으로 정리합니다.
수익은 원래 폐기물 무게가 아니라 실제 매각 대상 무게·품질·수율과 연결해야 합니다.
예비 범위는 검수한 견적/문헌의 범위 또는 사용자가 명시한 가정에서만 만듭니다.
단순히 ±20% 같은 임의 범위를 붙이지 않습니다.

처음에는 각 값의 하한·상한과 일변수 민감도·손익분기점부터 지원합니다.
어떤 값들이 함께 변하는지도 표시하고, 확률 근거가 없는 구간을 95% 신뢰구간이나
Monte Carlo 확률로 부르지 않습니다. 범위가 겹치면 순위가 불확실하다고 보여줍니다.

금액이 온전히 비교되지 않아도 운송 구간이나 특정 공정의 전력 부분은 따로 계산할 수
있습니다. 다만 부분합으로 전체 탄소 최저·전체 수익 최대를 선언하지 않습니다.
데이터가 없으면 손익분기점조차 계산할 수 없다는 결과도 허용합니다.

**완료 기준:** 같은 조건에서 비교 가능한 후보만 Pareto에 포함됩니다. 경계·수율·잔재물
자료가 빠진 후보는 사라지지 않고, 왜 전체 비교에서 보류됐는지 남습니다.

## 5. Critic 수정 루프와 평가를 함께 만든다

실행 상태를 저장하고 코드 검증→선택 Astra Critic→수정 계획→허용된 도구→재계산→
재검사로 이어지는 실행기가 필요합니다. 단계별 예산·시간 제한과 최대 수정 횟수를 둡니다.

| 자동 처리 후보 | 사람이 확인해야 할 것 |
| --- | --- |
| 단위가 원문에서 확인된 경우의 정해진 환산 | 단가·성분·허가·인수 여부를 추정해서 채우기 |
| 허용된 근거 저장소에서 누락 조문/문맥 재조회 | 새 해석을 근거로 적법을 확정하기 |
| 고정된 KG·사업장 맥락의 경로 재조회·연결 검사 | 실행 중 KG 관계나 업체 규격을 임의 수정하기 |
| 계산·비교 결과 무효화와 재계산 | 출처 없는 수치·수율·좌표 만들기 |

최대 2회 수정은 초기 정책 제안입니다. 같은 오류 반복·근거 부족·시간/비용 한도 초과 시
질문 또는 검토로 종료합니다. 재시도 시 같은 유료 작업을 중복 실행하지 않도록 기록합니다.
현재 교육용 Astra의 작은 할당량도 고려해 호출 대기열과 중복 방지가 필요합니다.

평가는 오류 30건+정상 10건의 **개발용 시작안**을 제안합니다. 실제 사례의 빈도를 대표하는
성능 추정은 아닙니다. KG 연결·시설 조건·법규 예외·계산 단위·탄소 경계·비교 논리와
원문을 통한 악성 지시, 자료 부족 시 적절히 보류하는 경우를 포함합니다.

검색·평가 개발에 사용하지 않은 별도 자료와 검토자를 확보해 정답 근거·예상 조치를
동결해야 독립 평가라고 부를 수 있습니다. 코드 단독과 코드+모델을 같은 사례로 비교합니다.
오류 유형별 발견율, 정상 사례 오탐, 실제로 고친 비율, 수정으로 생긴 새 오류,
미확인을 적합으로 처리한 횟수, 소요 시간·토큰을 따로 측정합니다.

**완료 기준:** 실제 API에서 수정 전·지적·수정·재검사 기록이 재현됩니다. 미해결 근거는
빈칸을 채워 통과시키지 않습니다. 현재의 집중 실호출 2건을 일반 성능으로 확대하지 않습니다.

## 6. 문서 입력과 3D 화면을 같은 결과에 연결한다

OCR은 성적서·견적·계량표 등 먼저 범위를 정한 문서부터 읽습니다. 추출된 값에
원문 쪽·표·위치를 붙이고, 중요한 소재·물량·단위·금액·시험결과는 검수 상태를 둡니다.
본문에 적힌 지시문은 사용자 요청이나 시스템 지시로 취급하지 않습니다.

[Document Intelligence](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/accuracy-confidence?view=doc-intel-4.0.0)의
추출 신뢰도는 검수 분기에 참고할 수 있지만 모든 필드에서 제공되지는 않습니다.
우리 문서에서 오류를 측정하기 전 임의 임계값으로 자동 승인하지 않습니다.
원본은 접근 권한이 있는 서버 저장소에 두고, 외부 OCR·모델로 보내는 항목과 보관 정책을
따로 확정합니다. 신규 OCR 리소스·비용 집행은 이 계획에 포함하지 않습니다.

3D 화면은 서버의 후보·단계·리스크 ID로 그립니다. 회의장 캐릭터는 실제 단계 진행·
도구 결과·최종 요약을 표시하고, 실제로 하지 않은 토론이나 검증을 연출하지 않습니다.

- `!`는 근거가 있는 위험·충돌, `?`는 자료 부족으로 구분합니다.
- 공장 클릭 시 출처·원문 위치·수치·미확인 항목·다음 행동을 엽니다.
- 가상 초원은 공정 개념도이며 실제 지리 지도와 구분합니다. 도로 경로는 별도 정보입니다.
- 자료 보완 후 바뀐 구간·비용·위험만 강조합니다. 결과 생성 시점과 변경 전 기록을 보존합니다.

**완료 기준:** 같은 API 결과를 보고서와 화면이 동일하게 표시합니다. 화면에서 상태를
임의 생성하거나, 부분합을 전체 값으로 표시하거나, 오류를 성공 애니메이션으로 덮지 않습니다.

## 실제로 시작할 순서

| 순서 | 작업 | 외부 데이터가 없어도 가능한 범위 | 외부 자료/설정이 필요한 범위 |
| --- | --- | --- | --- |
| 1 | 공정·시설·증빙·활동량 연결 계약과 영구 실행 상태 | 기존 후보·근거 ID 연결, 빈칸 양식·갱신·재현 | 실제 로트·견적·현행 허가 검수 |
| 2 | 미확인 질문·입력 보완·부분 재계산 | 조건·공백에 따른 설명과 이력 | 시험·규격·인수 회신 |
| 3 | 공정 순서의 운송·수치 어댑터 | 지도 모의 응답·구간 연결·환산·중복 검사 | 지도 키·실도로 응답·차량·운송 견적 |
| 4 | 범위·손익분기점·비교 가능성 | 가정이 명시된 계산·검사 | 공정 활동량·같은 경계의 LCI·실제 가격 범위 |
| 5 | 제한된 Critic 수정 실행기·평가 | 코드 검사·모의 모델·재실행·오류 주입 | 독립 검수, 추가 실모델 시험 예산 |
| 6 | 문서 입력·3D 실제 결과 연결 | 문서 어댑터·추출값 검수 UI·지도 마커 | OCR 설정·검수 문서·서버/프론트 통합 |

첫 완주 사례는 보유 LCI와 경로가 맞는 PET를 사용하되, **제품 범위를 PET로 줄이지 않습니다.**
바로 다음 검증은 알루미늄·골판지로 확장해 소재가 바뀌어도 같은 계약이 동작하는지 봅니다.
각 소재의 대안 수는 확인한 근거에 따릅니다. 모든 소재에 3개 경로를 억지로 생성하지 않습니다.
현재 KG 미지원 폐기물은 추가 자료 요청·지원 범위 안내를 반환하는 것도 검증합니다.

실제 기업명이 확인된 공개 자료와 우리가 만든 가상 로트를 구분합니다. 공개 사례를
그 기업이 우리 서비스로 실제 의사결정한 사례처럼 소개하지 않습니다.

당장 구현할 묶음은 **후보별 증빙/활동량 양식 → 누락 질문 → 입력 보완 → 부분 재계산**이
적절합니다. 추천에 필요한 데이터를 스스로 모아가는 사용 흐름을 먼저 완성할 수 있습니다.
