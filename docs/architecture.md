# Re:Source AI 구조

전체 목표와 단계 순서의 기준은 [공정·시설 추천 아키텍처 v2](pipeline-baseline.md)입니다.
이 문서는 그 목표와 **지금 코드로 실행되는 부분**의 연결을 설명합니다.

## 서비스 사이의 경계

~~~mermaid
flowchart LR
    Client[Re_client 화면·3D] --> Server[Re_server 인증·기업·업무 API]
    Server --> AI[Re_ai 후보 탐색·근거 검색·검증·계산]
    AI --> Neo4j[(Neo4j 지식그래프)]
    AI --> PG[(PostgreSQL·pgvector 법령 검색)]
~~~

클라이언트는 서버를 통해 AI를 호출합니다. 이 저장소는 회원·기업의 업무 DB나 화면을 구현하지 않습니다.
다른 저장소의 코드를 복사·import하지 않고, API 스키마로 요청·응답을 맞춥니다.

## 현재 실행되는 조사

POST /analysis/research는 구조화된 폐자원 정보를 받아 다음을 수행합니다.

1. /kg/assessed-plans와 같은 서비스를 통해 Neo4j의 공정·시설 후보를 모든 페이지에서 수집합니다.
2. 조회 버전·전체 건수·중복·단계 연결을 확인하고, 시설 공개 조건 대조 결과를 붙입니다.
3. 공정·시설·인계 구간별 확인 질문을 만들고 기존 로컬 법령 검색을 호출합니다.
4. 원문·조문·시행일·출처, 검색 실패·근거 없음·예산 초과와 미확인을 보존해 REVIEW로 반환합니다.

이 실행은 agents/research.py에 있습니다. 선택 필드 `legal_graph`를 주면 기본 Hybrid 검색 대신
별도 법률 그래프의 Researcher → Auditor → Adjudicator를 후보별로 실행합니다. 실제 모델 연결은 미실행이며
현재는 구조 적재와 가상 모델 테스트를 구분합니다. [법률 그래프 상세](legal-hierargraph.md)를 참고하세요.
현행 허가·실제 인수 검증, 적합성 종합 판정, 최종 순위는 아직 없습니다. 자료가 없다는 이유로 후보를 숨기거나 통과시키지 않습니다.
현재는 동기 실행이며 전체 단계의 영구 이력·진행 이벤트·취소·재시작 복구까지 구현한 실행기는 아닙니다.

추가된 `POST /analysis/review-template`은 같은 후보를 조회하되 RAG·모델을 호출하지 않고 경로별 빈 수치 양식을 만듭니다.
`POST /analysis/review`는 연구 서비스를 다시 호출하고 입력 해시·현재 KG 세대·공정/인계 ID와 순서·같은 투입 물량을 대조합니다.
올바르게 연결되고 계산 항목이 완성된 수치만 별도의 수치상 Pareto에 넣습니다. 나머지 경로와 누락·오류도 결과에서 보존합니다.
이 비교는 적합성 검증 통과나 최종 추천을 뜻하지 않습니다.

결정론적 Critic이 전체 후보의 연결·조건·계산·Pareto 층을 검사하며, `REVIEW / REVISE`와 원인 단계·후속 무효화 범위를 반환합니다.
후보별 다음 행동, Markdown 검토 보고서와 지도 마커 데이터까지 생성합니다. 의미적 모델 반박·PASS 게이트·최종 Top K·자동 부분 재실행·영구 이력·실제 화면 연결은 남았습니다.
[계약과 예제](grounded-decision-review.md)를 참고하세요.

## KG의 세 자료층

| 자료층 | 하는 일 | 해석하면 안 되는 것 |
| --- | --- | --- |
| W2RKG 원본 문헌 관계 | 폐기물·공정·산출물·참고문헌의 조사 후보 제공 | 공정 문자열의 나열을 검증된 실행 순서로 해석 |
| 별도 출처 기반 상태 전이·시설 연결 | 입력 상태에서 여러 공정 순서와 시설 조합 생성 | 공개 사례·사업장 역할 가설을 해당 로트의 인수 승인으로 해석 |
| 국내 시설 등록 명부 | 코드·설비 단어·지역·직선거리로 추가 조사 대상 검색 | 등록 기록을 현재 허가·여유 용량·실제 공정 수행의 확인으로 해석 |

온톨로지·출처 검사 → 격리된 메모리 적재 준비 → 새 Neo4j 세대 적재·감사 → 활성 세대 전환 순서로 적재합니다。
SQLite는 적재 전의 격리 검증에 사용하며 실제 KG 조회 DB는 Neo4j입니다. 장애 때 메모리 번들로 결과를 대신 만들지 않습니다.
조회는 허용한 고정 파라미터만 받으며, 후보·공정·시설·구간·근거 ID와 그래프 버전을 보존합니다.

주요 API는 목적에 따라 나뉩니다.

| API | 결과 |
| --- | --- |
| /kg/candidates | 기존 제한 문헌·공정 후보 조회 |
| /kg/candidate-pool | 문헌·기존 조건부 경로·조사 카드의 페이지 단위 전체 조사 묶음 |
| /kg/process-plans | 별도 상태 전이를 따르는 공정·시설 경로 후보 |
| /kg/planning-coverage | 활성 그래프의 자료 수·끊긴 가지·산출물 도달·시설 미연결 진단 |
| /kg/facility-candidates | 특정 공정 단계의 공개 시설 근거와 명부의 추가 조사 대상 |
| /kg/facility-assessment | 한 시설–공정 연결의 공개 조건 대조 |
| /kg/assessed-plans | 경로 생성과 단계별 공개 조건 대조 연결 |

공개 조건은 예시·명시적 제외 정책·미확인을 구분합니다. 후속 공정의 입력 상태는 KG의 예상 상태이며,
원래 로트의 성분·오염·수분 측정값을 그대로 복사하지 않습니다.
시설 역할·현장 수행·법규 적용성·실제 인수는 각각 별도의 확인 근거가 필요합니다.

제지 공정은 공개된 10개 작업을 5개 상태 전이로 연결합니다. PE 소재군과 사용자 입력 세부 수지를
구분하고, 등급별 적용은 미확인으로 보존합니다. 출처별 검수 연결 범위를 검사하며 연결 진단을
조사 응답까지 전달합니다. 이 진단은 전체 Critic의 실행 가능성 판정을 대신하지 않습니다.
[이번 KG 보강](kg-evidence-upgrade.md)을 참고합니다.

## 법령 검색과 수치 계산

법령 검색은 공식 문서를 수집·검증·청킹해 PostgreSQL에 적재합니다. multilingual-e5 벡터 검색과
tsvector 키워드 검색을 RRF로 결합하고 공식 출처·시행일·제목/조문 일치도로 재정렬합니다.
법령·판례는 문서 유형과 조·항·호, 사건번호·계층 경로로 구분하며 검색 성공을 적법성으로 바꾸지 않습니다.

POST /analysis/compare-scenarios는 별도로 제출된 수치·근거를 calculators/scenarios.py에서 계산합니다.
같은 물량·단위·연도·지역·시스템 경계를 검사하고, 공정·운송·잔재물 비용/탄소와 매각 수익을 다룹니다.
누락된 값은 미완성 총계로 남기며, 비교 가능한 수치 시나리오에 Pareto 층을 계산합니다.
실제 견적·도로거리·LCI를 찾거나 검증된 KG 후보를 최종 추천하는 API는 아닙니다.

분석 API의 기본 경로는 현재 외부 생성 모델 없이 동작합니다. 법률 그래프 선택 경로는 모델 설정과
특징·요건 생성이 필요합니다. 별도 화면 프로토타입의 모델 연동을
이 저장소의 전체 Agent 실행기 구현으로 간주하지 않습니다.
[분석 계약·예제·남은 범위](candidate-analysis.md)를 참고합니다.

## 이후에 연결할 전체 흐름

입력 추출·사용자 검수 → KG 전체 후보 → 법규·시설 검증·Auditor → 실제 수치 근거와 Python 계산 →
Pareto·잠정 Top K → 전체 후보를 보는 독립 Critic → PASS / REVISE / REVIEW → 최종 보고서·지도 순서입니다.

조사 내부의 검색·보완에는 제한된 ReAct를 사용할 수 있습니다. 수치 계산·단계 순서·분기·재시도 상한은 코드가 제어합니다.
Critic이 오류를 찾으면 원인 단계부터 다시 수행하고 영향받은 후속 결과를 무효화·갱신한 뒤 재검증합니다.
미확인 핵심 허가·인수 조건은 REVIEW로 남깁니다. 이 전체 흐름은 아직 연결되지 않았습니다.

## 데이터와 추적

- 번들 참조 자료는 knowledge_graph/resources/, 고정 W2RKG 인덱스는 data/knowledge_graph/에 둡니다.
- 공식 법령 재수집 결과·매니페스트는 Git에서 제외된 data/official/, 국내 명부 원본은 data/local/facilities/에 둡니다.
- 원본 출처·사용 조건·수집 범위·버전·해시를 함께 관리합니다. 제한 원본·키·DB 볼륨은 Git에 올리지 않습니다.
- API 형식과 서버 이벤트 계약은 서버 담당자와 맞춥니다. 스키마 변경 PR은 서버 담당자 리뷰·승인을 받습니다.

[데이터 관리](../data/README.md), [API 목록](api.md), [전체 문서 안내](README.md)에서 세부 실행 방법을 찾을 수 있습니다.
