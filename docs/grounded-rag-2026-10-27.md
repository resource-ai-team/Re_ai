# 법령 검색 보강

**비슷한 문단을 찾은 뒤, 원문에 명시된 상위법 조문도 함께 가져오도록 바꿨습니다.** 기존 E5 임베딩과 PostgreSQL·pgvector를 사용합니다. 10월 26일 확보한 법령·고시 98문서는 그대로 검색합니다.

## 무엇이 달라졌나요?

1. **조사 대상과 근거를 함께 조회합니다.** 지침의 목적 조문이나 시행령·시행규칙의 인용에서 실제로 명시한 상위 법령을 따라갑니다. 예를 들어 허가 지침이 폐기물관리법을 인용하면 해당 법의 근거 조문과 지침을 함께 보여줍니다. 질문별 정답 조문을 하드코딩한 목록은 없습니다.
2. **정의가 있는 별칭만 연결합니다.** `「법령명」(이하 “법”이라 한다)`를 원문에서 추출하고 같은 현재 문서에 그 정의가 실제로 있는지 다시 확인합니다. 다른 정의와 충돌하거나 특정 조문에만 한정된 정의는 문서 전체에 적용하지 않습니다.
3. **결과 중복을 줄입니다.** 같은 법령 버전의 조문·별표·지침 장에서 나온 여러 조각을 하나로 묶어 다른 근거도 볼 수 있게 합니다. 원문 전체 항·예외·명시 참조는 별도 문맥 조회에서 보충합니다.
4. **명시한 조문은 직접 조회합니다.** 한 현행 법령명과 한 조문이 명확하면 정확한 문서·조문 ID로 조회합니다. 현재 버전이 중복되거나 과거·부정·여러 조문이 섞인 요청은 이 직접 조회를 강제하지 않습니다. 일반 검색 결과가 법적 적용성을 확정하는 것은 아닙니다.
5. **Critic 전송량을 관리합니다.** 엔진의 후보·수치 사실을 유지하고, 기본 근거 → 검색 결과 → 참조 문맥 순으로 제공된 조문·별표 묶음을 선택합니다. 모델에 전송하지 못한 법령 자료의 수·문서명을 표시하고, 제외한 근거 별칭은 인용 검증 목록에서도 제거합니다.

상위법 연결도 **검색 근거**입니다. 해당 사업장에 적용되는지, 예외가 있는지, 실제 업체의 허가가 유효한지는 별도 검증 대상입니다. 현행 공개 법령만 대상으로 하고 기업 자료·다른 기업의 문서로 검색 범위를 넓히지 않습니다.

## 실제로 나아졌나요?

같은 로컬 E5·DB에서 기존 방식과 보강 방식을 비교했습니다. 기본 설정 선택에는 개발용 질문을 사용했고, 동결한 검증 질문은 결과 확인용으로 사용했습니다. 출처 지식이 가려진 독립 실험이나 전문가 법률 평가는 아닙니다.

| 점검 | 기존 방식 | 보강 방식 |
| --- | --- | --- |
| 개발용 법령 질문 | 8/16 | 15/16 |
| 기존 기본 법령 질문 | 5/7 | 7/7 |
| 기존 추가 표현 | 3/8 | 7/8 |
| 동결 검증용 법령 질문 | 6/14 | 8/14 |
| 신규 문서·조문 조회 | 15/15 | 15/15 |
| 분야 구분·명시 지침 조회 점검 | 4/7 | 6/7 |
| 검증용 기술 질문 | 9/9 | 9/9 |

지표는 기대한 근거가 Top 5에 있는지 보는 점검입니다. 8/14를 제품의 법률 정확도 57%로 해석하면 안 됩니다. 분야 구분 점검은 기능 진단에도 사용했으므로 독립 성능 지표로 보지 않습니다.

실제 PostgreSQL·Neo4j를 사용한 코드 테스트는 **870개 + 하위 검사 24개, 실패·skip 0개**입니다. 가상 PP 3톤 + 실제 KG/RAG/LCI + 모의 Azure에서는 HTTP 연결 검사 5개와 비정상/차단 사례 11개가 통과했습니다. 실제 GPT 호출·법률 추론 품질 평가는 이번에 수행하지 않았습니다.

시나리오의 Critic 입력은 102,285자입니다. 사용할 수 있는 법령 조각 121개 중 84개를 전송 대상으로 선택하고 37개를 제외했다고 표시합니다. 전체 RAG 보고서의 원문은 유지됩니다. **선택한 묶음도 법령 문서 전체나 모든 예외를 확보했다는 보장은 아닙니다.**

## 팀원이 적용하는 방법

기존 DB를 쓴다면 프로젝트 루트에서 실행합니다. 원문을 다시 임베딩하지 않고 정의 메타데이터를 보강합니다.

```powershell
resource-rag init-db
python scripts/build_legal_aliases.py --output data/official/legal-aliases.json
```

새 데이터를 넣을 때는 기존 수집·적재 절차를 사용합니다. 새 법령 적재와 확장 코퍼스 재실행에도 별칭 정의가 반영됩니다. 마이그레이션 `006_korean_lexical.sql`을 포함해 `init-db`를 먼저 적용해야 합니다.

기본 설정:

```dotenv
RETRIEVAL_LEGAL_BASIS=true
RETRIEVAL_KOREAN_LEXICAL=false
```

기본 상위법 연결은 추가 모델 설치나 외부 호출이 필요 없습니다. LEGAL 그룹 또는 명시한 법률 코퍼스에 적용하며 TECHNICAL·COMPANY 검색은 기존 범위를 유지합니다.

재현:

```powershell
python scripts/evaluate_grounded_rag.py --split dev --profiles legacy grounded --output data/official/grounded-dev.json
python scripts/evaluate_grounded_rag.py --split test --profiles legacy grounded --output data/official/grounded-test.json
```

## 응답에서 확인할 값

`GET /rag/search?search_group=LEGAL`과 파이프라인의 법령 근거에 다음 값이 추가됩니다.

| 값 | 의미 |
| --- | --- |
| `evidence_role=retrieved` | 일반 검색 결과 |
| `evidence_role=cited_basis` | 검색된 규정이 명시적으로 인용한 상위 근거 |
| `evidence_role=explicit_locator` | 사용자가 명시한 현행 법령·조문 직접 조회 |
| `reference_sources` | 상위 근거를 인용한 공개 원문 조각 ID |
| `legal_context.alias_definitions` | 원문에서 대조한 별칭 정의·출처 |

응답 순서는 일반 근거와 상위법을 함께 보여주는 순서입니다. `score`를 법적 적합성 확률이나 서로 다른 검색 경로의 절대 점수로 비교하면 안 됩니다.

Critic의 `coverage`에는 `available_legal_evidence_count`, `selected_legal_evidence_count`, `omitted_legal_evidence_count`, `omitted_legal_by_document`, `all_legal_contexts_included`가 추가됩니다. 누락이 있으면 모델이 전체 법령을 검토했다고 볼 수 없습니다.

## 남은 문제와 실험

- 검증용 법령 질문 6개는 아직 기대 조문을 Top 5에 회수하지 못합니다. 추가 표현 질문도 1개 남았습니다.
- 화학물질 취급 질문에서 기대한 일반 취급기준 대신 시설·진열 관련 조문이 상위에 오는 사례가 있습니다. 라벨과 실제 적용 범위를 전문가가 함께 확인해야 합니다.
- 자료 확장 전 검증용 법령 점수 10/14까지 회복한 상태는 아닙니다.
- 한국어 형태소 검색도 구현·색인했지만, 초기 개발 질문에서 단독 적용은 3/16, 중복 억제와 함께 적용해도 5/16이어서 기본은 비활성입니다. 외부 질문 전송·질문 캐시 없이 로컬에서만 처리합니다.
- 키워드 검색이 0건인 원인은 확인했지만 형태소 검색 추가만으로 해결했다고 보지 않습니다. 기본 적용한 개선은 인용 관계·문서 구조를 이용한 근거 보강입니다.
- 일반 검색은 현행 코퍼스 참고 자료입니다. 과거 법령 적용, 전문가 Auditor, 실제 허가·인수 확인을 완료한 결과가 아닙니다.

형태소 실험을 재현할 때만 `pip install -e ".[korean-lexical]"` 후 `scripts/build_korean_legal_index.py --output data/official/korean-index.json`을 실행합니다. E5 벡터·원문을 변경하지 않는 별도 검색 열을 사용합니다. 기본 서비스 사용에 이 실험은 필요하지 않습니다.
